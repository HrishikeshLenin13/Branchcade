## Independent review protocol

The owner proposes Claude Opus 5.5 and GPT Astra if those models are available in the actual environment. These are requested reviewer names, not verified availability or agents launched here. The owner must separately authorize the audit. Each reviewer first fetches clean main, reads SPEC in full, records its SHA/runtime/tool inventory, and independently writes findings before seeing the other review. Use browser/development MCP where present and ordinary Playwright/CLI otherwise; disclose exactly which tools actually ran.

Give each reviewer the same immutable source checkpoint and separate synthetic browser profiles. Source reading, automated tests and observed UI behavior require separate evidence columns; acceptance reports are navigation aids, not proof. Complete an initial read-only independent findings round before reconciling. Then reproduce each disagreement, retain both observations, agree severity and ownership, and serialize fixes on main so reviewers never overwrite one another. Fetch before every edit and fast-forward only clean work; no new branches, PRs, history rewriting or force pushes under the current policy. Stop if local and remote diverge; preserve both histories and request coordination.

Every finding needs requirement reference, reproduction steps, expected/observed values, exact source SHA, browser/version/viewport, console/network/error context, screenshot or trace path and data classification. Use synthetic aliases only. A screen rendering does not prove a control works. A clean automated suite does not establish every SPEC requirement. Do not mark a human review or classroom result complete by automation.

## Reconciliation and repair order

- P0: crash, incorrect physics, corruption, invalid learning evidence, broken persistence, privacy/security. Reproduce immediately, contain exposure if relevant, repair the authoritative source and add a meaningful regression. Engineering release waits for closure.
- P1: broken controls/navigation, inaccessible core interactions, confusing learning flows or incorrect feedback. Validate through real user actions after repair.
- P2: layout, responsiveness, animation, large-workspace performance, error-state consistency. Measure and compare before optimizing.
- P3: accounts/sync, instructor sharing, approved-logo integration and curriculum extensions. Separate requirements and approval first.

After each coherent repair: relevant unit/browser tests; full maintained gates before final push; inspect GitHub CI including retry markers. Preserve original failure evidence. A “fixed” row requires new source SHA and passing reproduction; do not close a bug from code inspection alone. Reconcile findings in a later report, keeping each reviewer's independently written original. No speculative redesign to manufacture defects.

## Later optional account and sync requirements

**Decision gate:** demonstrate a real cross-device need after the audit. Current export/import may be sufficient. Keep anonymous local mode usable without login; do not make robotics practice depend on an account. No provider/account/backend is selected or implemented here.

Current persistence is one `branchcade-local` IndexedDB v1 `app/state` envelope, written through `src/app/session.ts` and validated by `domain/schemas.ts`. It includes active/inactive pseudonyms, attempts, drafts, saved labs, assignments and local teams. Prediction/program/world/trace hashes bind immutable executed evidence; hashes do not authenticate a user's identity. These existing contracts and historical execution versions must survive any migration.

The current recommendation is to retain local mode/export-import until the audit establishes an unmet cross-device need. Managed OIDC/authentication could reduce password/session implementation work but adds provider terms, data processing, recovery and cost obligations. School-managed identity could reduce separate learner credentials but adds district integration, tenant/roster authorization and consent questions. A self-hosted mature identity service adds patching, incident response and availability work; bespoke password authentication is a poor default for this small project. No vendor is selected from remembered features or prices.

If sync is separately approved after the audit, the candidate design is to keep IndexedDB authoritative for offline UI and put a versioned, validated outbox/sync adapter behind it. An authenticated server would authorize per-owner immutable records in a database, with separate draft revisions and explicitly approved teacher grants. It would never accept client ownership claims or an unreviewed whole-envelope overwrite. This fits the existing append-only evidence contracts better than replacing local storage outright; it remains a conditional proposal requiring a threat model, migration design and privacy review.

The audience includes under-13 learners. An owner and qualified privacy reviewer must decide applicable obligations and parent/school roles before collecting remote identifiers or child records. The [FTC guidance](https://www.ftc.gov/business-guidance/resources/complying-coppa-frequently-asked-questions), checked 2026-10-24, flags the revised COPPA rule and discusses notice, consent, access/deletion, security and retention. Pseudonyms, optional collection or school involvement do not by themselves settle applicability. This document is a design gate, not compliance certification. Review current law, school contracts and provider terms for the actual deployment before approval.

Acceptance for later sync must include offline-two-device conflict cases, mixed historical records, account isolation attacks, consent withdrawal, recovery, full deletion including returning offline clients, data export and preserved anonymous mode.
